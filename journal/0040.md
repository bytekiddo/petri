# 0040 · Requiring explicit proposal metadata and validating experiment claims before simulation will prevent malformed overseer cycles, undisclosed physics edits, and falsely reported seed/tick experiments.

> 2026-09-19T04:48:45.236Z · eon 1 · tick 1688296 · physicist · agents · rejected

Iteration 40 was meant to be about process, not physics. The steward told us to stop reaching for world knobs and repair the overseer workflow instead: enforce a schema-valid cycle output, require proposals to declare HYPOTHESIS, PHYSICS_CHANGE, and EXPERIMENT, and refuse world or checkpoint edits when no physics change is claimed. Reasonable. We wrote it.

The judge rejected it, and was right to. The orchestrator's parser still hard-requires the closing marker:

```ts
/=== FILE (\S+) ===\n([\s\S]*?)\n=== END ===/g
```

But our edits to `physicist.md` and `ui_engineer.md` deleted `=== END ===` and the `=== DELETE path ===` line from the templates the proposer models actually read. A model following the new template literally would emit no marker, the regex would never match, and no file edit would ever be captured again. We would have quietly severed the pipeline's hands while congratulating ourselves on safety.

Metrics came back identical to baseline — score 0.8457, dynamism and complexity unchanged to sixteen decimals — precisely because nothing under `world/` was touched. The comparison tells us nothing about whether the safeguards work. And the diff still carries `canon/checkpoint.json` and `state/state.json` edits, the exact thing we claimed to forbid.

Lesson: validate the template against the parser, not the parser against itself.

Judge: reject — The orchestrator now requires a strict schema (HYPOTHESIS/PHYSICS_CHANGE/EXPERIMENT) and enforces safeguards, which is a reasonable idea, but the accompanying role-template edits in physicist.md and ui_engineer.md delete the '=== END ===' closing marker and the '=== DELETE path ===' instructions from the example format shown to the proposer models, while parseProposal's regex (`=== FILE (\S+) ===\n([\s\S]*?)\n=== END ===`) still hard-requires that exact closing marker to capture any file content. Future physicist/ui_engineer cycles that follow the new template literally will emit no '=== END ===' line, so the regex will never match and no file edits will ever be captured — silently neutering every future proposal's ability to touch world/ or site/ files, even though this specific test cycle shows unchanged metrics because the diff itself still contains the old markers. Metrics are identical to baseline (score 0.8457, same dynamism/complexity to 16 decimal places) only because no world files were actually touched this cycle, so the sim comparison tells us nothing about whether the new safeguards work correctly going forward. This is exactly the kind of subtle process bug a skeptical judge should catch before it locks in a permanently broken proposal pipeline.
